## 3. MVP 범위

본선 MVP의 지원 제품군은 다음 두 종으로 제한한다.

- 모발건조기
- 일반 보온용 전기방석

제품군을 임의로 추가하지 않는다. LED 조명 등 검토 후 채택하지 않은 아이디어는 현재 MVP 구현 범위에서 제외한다.

### 3.1 모발건조기 역할

- 예선 기획과 기존 Rule Engine 구현의 연속성을 유지하는 첫 번째 기준 제품
- 비교적 명확한 제품 분류와 공식 자료를 기반으로 안정적인 기본 진단 흐름을 시연
- 신규 제품군 추가로 인해 기존 모발건조기 Rule과 결과가 변하지 않도록 회귀 테스트 수행

### 3.2 일반 보온용 전기방석 역할

- 봉제·생활소품 소공인의 실제 제조 상황을 보여주는 두 번째 제품
- 방석에 열선·온도조절기·어댑터 등을 결합했으나 KC 절차와 준비자료를 알기 어려운 상황을 대표 시나리오로 사용
- 치료·통증 완화 등 의료적 표현이 있는 경우 전문가 확인사항으로 분기하며 의료기기 해당 여부를 서비스가 직접 판정하지 않음

### 7.1 컨설턴트

- 상담 완료·취소 및 처리 이력 확인

컨설턴트 내부 메모는 소공인 사용자에게 공개하지 않는다.

### 7.2 관리자

- 사용자·컨설턴트 계정과 역할 관리
- 컨설턴트 계정 승인
- 제품군·질문·Rule·준비도 기준 관리
- 공식 문서 메타데이터·정제·색인 관리
- RAG 품질 점검
- 리포트 문구와 AI 장애 폴백 설정 관리
- 상담 전체 현황, 감사 로그와 서비스 상태 확인

화면에서 메뉴를 숨기는 것만으로 권한을 제어하지 않는다. Web과 Android의 모든 보호 기능은 백엔드 API에서도 역할·소유권을 검증해야 한다.

## 9. AI·Rule·RAG 판정 원칙

- Rule Engine이 인증 검토 후보와 구조화된 결과를 결정한다.
- LLM은 검색된 공식자료를 근거로 사용자 이해를 돕는 설명문을 생성한다.
- LLM이 인증 유형, 안전 적합·부적합 또는 최종 인증 결과를 임의 생성하지 않는다.
- RAG 근거가 부족하거나 제품 조건과 일치하지 않으면 추측하지 않고 ‘확인 필요’로 표시한다.
- 다른 제품군 전용 문서를 우선 근거로 사용하지 않는다.
- 동일 Rule 버전과 동일 입력에는 가능한 한 일관된 구조화 결과를 제공한다.
- 준비도 점수는 공식 요구자료 대비 현재 준비 수준이며 인증 합격 확률이 아니다.
- 서비스 결과는 최종 인증 판정, 시험·심사 결과, 법률 자문 또는 인증 대행을 대체하지 않는다.

### 9.1 AI 장애 폴백

AI/RAG Worker의 장애·타임아웃·근거 부족 상황에서도 Rule Engine 결과와 구조화된 기본 리포트는 유지한다. 근거 기반 설명은 승인된 템플릿과 오류 안내로 대체하며, 장애 상황에서 LLM이 임의 답변을 생성하지 않도록 한다.

### 9.2 공식 문서 관리 기준

공식 문서는 가능한 범위에서 다음 메타데이터와 함께 관리한다.

- 발행기관
- 문서명
- 적용 제품군
- 제도·인증 유형
- 대상 조건
- 제출자료
- 표시·라벨링 기준
- 예외·전문가 확인 조건
- 발행일·확인일·적용 기준일 또는 버전
- 원문 URL
- 정제·색인 상태

공식 출처와 원문 링크를 우선 사용하며, 기준일과 적용 범위가 불명확한 문서는 확정 근거로 사용하지 않는다.

## 11. 보안 원칙

API 키, 토큰, 비밀번호, 시크릿, 환경변수, 인증서, 실제 개인정보를 코드·문서·프롬프트·로그·스크린샷·공개 저장소·공모전 제출물에 포함하지 않는다.

- 민감정보는 환경변수 또는 승인된 시크릿 관리 방식으로 보관
- `.env`, credentials, 인증서 파일은 저장소와 공유 문서에서 제외
- 테스트에는 가상 계정과 가상 상담 데이터를 사용
- 민감정보가 발견되면 그대로 재출력하지 않고 마스킹
- 외부 공개 또는 팀 공유 전 키·토큰·개인정보 포함 여부 확인
- 민감정보를 공개 저장소나 제출물에 올려야 하는 상황이 발생하면 먼저 PM에게 대상·위치·필요성을 설명하고 명시적 승인을 받은 후 진행

## 12. 변경관리 원칙

- 확정사항, 미정사항, 구현사항, 일부 구현, 미구현, MVP 제외를 구분
- 미정사항을 임의로 구현 기준으로 확정하지 않음
- 멘토링이나 팀 회의로 변경된 내용은 변경일, 변경 전, 변경 후, 변경 사유와 영향 범위를 기록
- 변경 시 Android, Web, Backend, AI·데이터, DB, QA 영향 범위를 함께 확인
- 최신 정의서 변경이 코드에 반영되었는지 구현 추적표와 테스트로 검증
- 이미 확정된 사항을 반복 논의하지 않고, 변경 요청이 있을 때만 근거와 영향 범위를 재검토
- 기능 ID와 요구사항 ID를 가능한 한 유지해 문서·코드·테스트 간 추적성을 확보

## 13. 답변 및 산출물 작성 방식

- 현재 프로젝트에 업로드된 최신 파일을 기준으로 답변
- 해야 할 일을 담당 영역·우선순위·선행조건·완료기준 중심으로 정리
- 요청받지 않은 코드·문서·UI는 임의 변경하지 않음
- 확정되지 않은 내용을 사실처럼 작성하지 않음
- 팀 메신저 문장은 바로 복사할 수 있는 형태로 작성
- 보고서와 발표자료는 필요한 문장에 `[1]`, `[2]` 형태의 출처 번호를 표시하고 문서 끝에 ‘주요 참고자료’를 정리
- 외부 공개 산출물에는 개인 이름과 민감정보를 불필요하게 넣지 않음
- 실제 구현된 기능, 검증된 데이터와 시연 가능한 범위만 발표
- 과장된 표현, 자동 판정으로 오해될 수 있는 표현, 합격 확률로 오해될 수 있는 표현을 사용하지 않음
