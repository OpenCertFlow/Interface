# ADR-0004. AI 워커를 별도 프로세스로 분리

- 상태: 채택
- 날짜: 2026-07-10
- 결정자: 백엔드·인프라 (장근창), AI·데이터 (이준엽)

## 맥락

RAG 파이프라인(임베딩, Qdrant 검색, 리랭킹)과 LLM 프롬프트 오케스트레이션이 필요합니다. 이 영역의 도구 생태계는 Python에 있습니다. 담당자(이준엽)의 작업 언어도 Python입니다.

백엔드는 Java/Spring Boot입니다.

## 결정

**AI/RAG 워커를 FastAPI 기반 별도 프로세스로 분리**하고, 백엔드와 HTTP/JSON으로 통신합니다.

백엔드는 `SearchEvidencePort`, `NarrateReportPort` 두 개의 아웃바운드 포트로만 워커를 봅니다. 워커 API 스펙은 이 포트 인터페이스로부터 도출합니다.

```
POST /search    { schemeCodes, certificationTypes, productGroup, sections } → Evidence[]
POST /narrate   { profile, candidates, checklist, evidences }               → Narration
```

## 근거

**언어 경계가 곧 프로세스 경계입니다.** Java에서 Python RAG 스택을 부르는 방법(GraalPy, 프로세스 브리지, JNI)은 전부 HTTP보다 나쁩니다. Java 네이티브 벡터 검색으로 옮기는 것은 담당자의 역량을 버리는 일입니다.

**독립적으로 개발·배포되어야 합니다.** AI 담당자가 임베딩 모델을 바꾸거나 리랭커를 추가할 때 백엔드를 재배포하면 안 됩니다. 반대로 백엔드가 룰을 고칠 때 워커를 건드리면 안 됩니다. 3주 일정에서 두 사람의 작업이 서로를 막지 않는 것이 중요합니다.

**포트가 스텁을 허용합니다.** 워커가 완성되기 전에도 백엔드는 `StubEvidenceSearchAdapter`로 진단 흐름 전체를 돌리고 테스트할 수 있습니다. 실제로 일정표상 백엔드 API 구현(7.31~8.3)과 RAG 구조 구현이 같은 주에 잡혀 있습니다. 이 둘이 직렬로 묶이면 일정이 무너집니다.

**장애 격리가 필요합니다.** [ADR-0003](0003-rule-engine-over-llm.md)에 따라 RAG와 LLM은 실패해도 진단이 완료되어야 합니다. 프로세스가 분리되어 있으면 워커가 죽어도 백엔드는 살아 있고, 타임아웃과 폴백이 자연스럽게 표현됩니다. 같은 프로세스 안이라면 OOM 하나가 전부를 죽입니다.

## 결과

**얻는 것**

- 각자의 언어로 각자의 문제를 풉니다.
- 워커 장애가 진단 실패로 번지지 않습니다.
- 백엔드가 워커 없이 개발·테스트·데모 가능합니다.
- 워커를 별도로 스케일할 수 있습니다 (임베딩은 CPU를 많이 씁니다).

**치르는 것**

- 네트워크 홉이 추가됩니다. 진단당 2회 왕복, 각 수십 ms의 오버헤드. LLM 호출이 수 초인 것에 비하면 무시할 수준입니다.
- **API 계약 관리 비용**이 생깁니다. 두 사람이 서로 다른 스키마를 가정하면 통합 당일에 발견됩니다.
- 로컬 개발 환경에 컨테이너가 하나 더 필요합니다.
- 분산 추적이 필요합니다 — 백엔드 로그와 워커 로그를 잇는 무언가.

**완화**

- **API 계약을 먼저 고정합니다.** 7.27~7.30 데이터·규칙 설계 주간에 `/search`, `/narrate` 요청·응답 JSON 스키마를 확정하고 `docs/api/ai-worker.md`에 기록합니다. 이후 변경은 양측 합의로만.
- 백엔드는 `StubEvidenceSearchAdapter`를 `local` 프로파일 기본값으로 둡니다. 워커 없이 `./gradlew bootRun`이 돌아야 합니다.
- 백엔드가 생성한 `traceId`를 `X-Trace-Id` 헤더로 워커에 전파하고, 워커는 이를 로그에 찍습니다. 이것이 분산 추적의 최소 형태이며 해커톤에는 충분합니다.
- 타임아웃을 명시합니다: `/search` 2초, `/narrate` 5초. 초과 시 폴백.

## 대안

**Java 단일 프로세스에서 RAG까지 처리.** Spring AI + Qdrant Java 클라이언트로 가능합니다. 배포 단위가 하나로 줄어드는 이점이 실재합니다. 기각 사유는 사람입니다 — AI 담당자가 Java로 RAG 품질을 튜닝해야 하고, 그것이 이 프로젝트에서 가장 실험적인 반복이 잦은 영역입니다.

**메시지 큐(Kafka/Redis) 기반 비동기 연동.** 진단이 동기 요청-응답이므로 큐는 지연만 늘립니다. 문서 수집·색인 파이프라인은 배치이므로 큐가 어울리지만, 그것은 워커 내부의 관심사입니다. 기각.

**gRPC.** 스키마가 강제되고 성능이 좋습니다. 프로토 정의·코드 생성 파이프라인이 두 언어에 붙어야 하고, 해커톤 규모에서 얻는 것보다 설정이 큽니다. 호출량이 진단당 2회입니다. 기각.
