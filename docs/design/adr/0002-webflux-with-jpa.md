# ADR-0002. WebFlux + JPA 조합과 블로킹 격리

- 상태: 채택
- 날짜: 2026-07-10
- 결정자: 백엔드·인프라 (장근창, 오태훈)

## 맥락

기획서는 백엔드를 **Spring Boot WebFlux**로 명시했습니다. 진단 한 건이 RAG 워커와 LLM API를 순차 호출하며 수 초를 기다리므로, 요청당 스레드를 점유하지 않는 논블로킹 모델은 이 워크로드에 실제로 맞습니다.

문제는 영속성입니다. WebFlux의 정석 조합은 R2DBC이지만, R2DBC는 JPA가 제공하는 것을 주지 않습니다 — 연관관계 매핑, 영속성 컨텍스트, 지연 로딩이 없어 애그리거트 저장/로드를 손으로 조립해야 합니다. `Diagnosis` 애그리거트는 7개 자식 컬렉션을 가집니다.

팀 6명 중 백엔드는 2명이고, 3주 안에 룰 엔진·점수 로직·API·CI/CD·테스트를 끝내야 합니다.

## 결정

**WebFlux를 유지하고 영속성은 JPA를 사용합니다.** 모든 블로킹 JDBC 호출은 전용 `Scheduler`(`jdbcScheduler`)로 격리하며, 이벤트 루프에서는 절대 실행되지 않습니다.

격리는 `BlockingBridge`라는 단일 진입점을 통해서만 이루어집니다.

```java
// application 계층은 이렇게만 DB를 만진다
return blockingBridge.mono(() -> loadRuleSetPort.loadActive(productGroup))
        .flatMap(ruleSet -> ...);
```

`jdbcScheduler`의 스레드 수는 **HikariCP 최대 커넥션 수와 동일**하게 설정합니다.

## 근거

이 결정은 순수성을 실용성과 맞바꾼 것입니다. 그 교환을 명시적으로 적어 둡니다.

**WebFlux를 버리지 않는 이유.** 이 서비스의 지연은 DB가 아니라 **외부 AI 호출**에서 발생합니다. 진단 한 건에서 PostgreSQL 조회는 수 밀리초, RAG + LLM은 수 초입니다. 논블로킹의 이득은 압도적으로 후자에 있고, 그 구간은 `WebClient`로 완전히 논블로킹입니다. DB 구간만 스레드를 쓰는 것은 전체 그림에서 작은 비용입니다.

**R2DBC를 버리는 이유.** `Diagnosis` 애그리거트를 R2DBC로 저장하려면 7개 자식 테이블에 대한 삽입·삭제·조회를 손으로 조율하고, 트랜잭션 경계를 직접 관리하며, 로드 시 부모-자식을 조립해야 합니다. 이 코드는 재미없고 버그가 잘 숨습니다. 3주 일정에서 이 시간은 룰 20~30개를 정확하게 만드는 데 써야 합니다. 그것이 심사 대상입니다.

**스레드 수를 커넥션 풀 크기에 맞추는 이유.** `jdbcScheduler`가 커넥션 수보다 많은 스레드를 가지면, 초과분은 `HikariPool.getConnection()`에서 블로킹된 채 대기합니다. 스레드는 쓰이지도 못하고 메모리만 먹습니다. 반대로 적으면 커넥션이 놉니다. 두 값은 하나의 논리적 설정이며, `application.yml`에서 나란히 둡니다.

```yaml
certimakers:
  blocking:
    jdbc-pool-size: 10   # ← 아래와 반드시 같은 값
spring:
  datasource:
    hikari:
      maximum-pool-size: 10
```

**헥사고날이 이 결정을 되돌릴 수 있게 만듭니다.** 영속성 어댑터는 `SaveDiagnosisPort` / `LoadDiagnosisPort` 뒤에 있습니다. 본선 이후 R2DBC로 옮기고 싶다면 어댑터 하나를 갈아 끼우면 되고, 도메인과 애플리케이션은 한 줄도 바뀌지 않습니다. 지금 R2DBC를 강행하는 것보다 이 옵션을 열어 두는 편이 낫습니다. 이것이 [ADR-0001](0001-hexagonal-architecture.md)이 지불한 매핑 비용의 첫 번째 배당입니다.

## 결과

**얻는 것**

- 외부 AI 호출 구간에서 스레드를 점유하지 않습니다 — WebFlux의 실익을 전부 챙깁니다.
- JPA로 애그리거트 저장/로드를 짧게 씁니다.
- 팀의 기존 역량을 그대로 씁니다.

**치르는 것**

- **개발자가 규율을 지켜야 합니다.** `blockingBridge`를 빼먹고 리포지토리를 직접 호출하면 이벤트 루프가 막히고, 부하가 낮은 시연 환경에서는 증상이 안 보입니다. 이것이 이 결정의 진짜 위험입니다.
- 스레드 컨텍스트 스위칭이 추가됩니다. 무시할 수준입니다.
- `@Transactional`이 리액티브 체인을 가로지르지 않습니다. **트랜잭션은 어댑터 내부에서 시작하고 끝나야 합니다.** 애플리케이션 서비스에 `@Transactional`을 붙이면 동작하지 않습니다.

**완화 — 규율을 자동화로 대체합니다**

1. **BlockHound**를 테스트 프로파일에 붙입니다. 이벤트 루프에서 블로킹 호출이 발생하면 테스트가 즉시 실패합니다. 이것이 1차 방어선입니다.
2. `BlockingBridge`를 유일한 진입점으로 두고, 코드 리뷰 체크리스트에 "리포지토리 직접 호출 없음"을 넣습니다.
3. `application` 계층에 `@Transactional`이 있으면 ArchUnit이 실패하도록 규칙을 추가합니다.

## 대안

**WebFlux + R2DBC.** 아키텍처적으로 가장 깨끗합니다. `Diagnosis` 애그리거트 매핑 비용과 팀 러닝커브가 3주 일정에 맞지 않아 기각. 본선 이후 재검토합니다.

**Spring MVC + JPA + Java 21 가상 스레드.** 실은 이것이 이 워크로드의 가장 세련된 답일 수 있습니다. 블로킹 코드를 그대로 쓰면서 외부 호출 대기 중 캐리어 스레드를 반납합니다. 기각 사유는 순수 기술적이지 않습니다 — 기획서에 WebFlux가 명시되었고, 발표에서 "기획서와 다르게 구현했다"를 설명하는 비용이 실익보다 큽니다. 또한 현재 툴체인이 JDK 17입니다.

**MVC + JPA (가상 스레드 없이).** 진단 한 건이 수 초간 스레드를 점유합니다. 시연 중 동시 요청이 몇 건만 들어와도 톰캣 스레드가 고갈됩니다. 기각.
