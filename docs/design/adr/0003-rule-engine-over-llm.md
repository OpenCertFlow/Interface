# ADR-0003. 판정은 Rule Engine, 문장화만 LLM

- 상태: 채택
- 날짜: 2026-07-10
- 결정자: 전체

## 맥락

OpenCertFlow는 사용자에게 "당신의 제품은 안전확인 대상으로 보입니다"라고 말합니다. 이 문장이 틀리면 소공인은 잘못된 서류를 준비하고 시간과 비용을 잃습니다.

LLM은 이런 문장을 매우 유창하게, 그리고 때때로 완전히 틀리게 생성합니다. 같은 질문에 두 번 다르게 답하기도 합니다. 기획서는 성과지표로 "동일 입력 결과의 일관성"을 내걸었습니다.

## 결정

시스템을 **결정론 영역**과 **확률론 영역**으로 나누고, 둘 사이에 단방향 경계를 둡니다.

| | 결정론 (Java 도메인) | 확률론 (AI 워커) |
| --- | --- | --- |
| 인증 후보 식별 | ✅ Rule Engine | ❌ |
| 필수 서류 결정 | ✅ Rule Engine | ❌ |
| 준비도 점수 산정 | ✅ ScoreCalculator | ❌ |
| 표시·라벨링 항목 | ✅ Rule Engine | ❌ |
| 공식 근거 문단 검색 | ❌ | ✅ RAG |
| 리포트 문장 생성 | ❌ | ✅ LLM |
| 다음 행동 제안 | ❌ | ✅ LLM |

**AI 워커의 응답은 진단 판정을 변경할 수 없습니다.** 근거(`Evidence`)를 첨부하거나 설명(`Narration`)을 채울 뿐입니다. 코드 수준에서 `Diagnosis.attachEvidence()`와 `attachNarration()`은 후보·서류·점수 필드를 건드리지 않습니다.

RAG가 임계 유사도(0.65) 이상의 근거를 찾지 못하면, 억지로 문단을 붙이는 대신 `ExpertReviewItem(reason = NO_EVIDENCE)`을 생성합니다.

## 근거

**환각의 비용이 비대칭입니다.** LLM이 "안전확인 대상입니다"를 놓치면 사용자는 인증 없이 판매를 시도합니다. 반대로 시스템이 "판단할 수 없습니다, 전문가에게 확인하세요"라고 말하면 사용자는 잠깐 답답할 뿐입니다. 두 실패의 비용이 완전히 다르므로, 불확실할 때 침묵하는 쪽으로 편향시킵니다.

**규칙 20~30개는 LLM이 필요 없는 규모입니다.** "전기 사용 + 정격전압 50V 초과 + 어린이용 아님"은 boolean 표현식입니다. 여기에 확률 모델을 쓰는 것은 도구 오용입니다.

**LLM은 잘하는 일이 따로 있습니다.** "안전확인대상전기용품의 안전기준 부속서에 따른 시험성적서를 제출하여야 한다"를 "KTC나 KTR 같은 시험기관에서 시험성적서를 받아 오세요"로 바꾸는 일. 이것이 기획서가 말한 "복잡한 인증 문구를 쉬운 다음 행동으로" 바꾸는 작업이며, 판정과는 무관합니다.

**결과가 재현 가능해야 합니다.** 룰 평가는 순수 함수이므로 같은 입력 + 같은 룰셋 버전은 항상 같은 판정을 냅니다. 진단 결과에 `rule_set_version`과 `matched_rule_codes`를 저장하여, 사후에 "왜 이 후보가 나왔는가"를 룰까지 역추적합니다. LLM이 판정에 개입하면 이 추적 가능성이 사라집니다.

## 결과

**얻는 것**

- 같은 입력에 같은 판정. 성과지표 "결과의 일관성"을 정의상 만족합니다.
- LLM 실패가 진단 실패가 아닙니다. 문장만 템플릿으로 폴백합니다 ([03-diagnosis-flow.md](../03-diagnosis-flow.md#34-장애-폴백-정책)).
- 심사위원의 "환각은 어떻게 막나요" 질문에 아키텍처 다이어그램으로 답합니다.
- LLM 비용이 진단당 1회 호출로 고정됩니다.

**치르는 것**

- 룰에 없는 제품은 진단하지 못합니다. 커버리지가 곧 서비스 가치이며, 룰 작성이 병목이 됩니다.
- "AI 서비스인데 AI가 판단을 안 하네요"라는 인상을 줄 수 있습니다. **발표에서 이것을 약점이 아니라 설계 의도로 제시해야 합니다.**
- 룰 유지보수 비용이 지속적으로 발생합니다.

**완화**

- 룰이 아무것도 매칭하지 못한 경우를 `UNKNOWN` 경로로 명시 처리하여, 침묵이 아니라 "전문가 확인 필요 + 컨설팅 연결"이라는 유효한 사용자 가치로 전환합니다.
- 룰을 JSON으로 DB에 두어(`R__seed_rules.sql`) 비개발자도 추가할 수 있게 합니다.

## 대안

**LLM이 판정하고 RAG로 근거를 붙인다 (전형적인 RAG 챗봇).** 구현이 훨씬 빠르고, 룰 작성이 필요 없으며, 커버리지가 즉시 넓습니다. 그리고 인증 여부를 자신 있게 틀리게 말합니다. 이 도메인에서는 받아들일 수 없습니다. 기각.

**LLM이 판정하고 Rule Engine이 검증한다.** 룰이 LLM 출력을 사후 검사하는 구조. 결국 룰을 다 만들어야 하므로 룰 작성 비용은 같은데, LLM 호출이 늘고 불일치 시 처리가 복잡해집니다. 기각.

**Rule Engine이 판정하고, 매칭 실패 시에만 LLM이 추정한다.** 매력적으로 들리지만, LLM이 개입하는 경우가 정확히 "룰이 모르는 어려운 케이스"입니다. 가장 위험한 곳에서 가장 신뢰할 수 없는 도구를 씁니다. 기각 — 이 경우는 전문가 상담으로 보냅니다.
